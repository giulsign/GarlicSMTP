6. PROBLEMA AFFRONTATO: MESSAGGI APPARENTEMENTE BLOCCATI IN QUEUE
==============================================================================

6.1 Sintomo
-----------
Alcuni messaggi, sia in ambiente developer sia in VM, rimanevano pending per tempi molto lunghi. L'obiettivo era capire se esistesse uno stall reale e consentire un nuovo tentativo quando il destinatario Tor tornava raggiungibile, senza rompere le semantiche di delivery.

6.2 QueueWorker osservato
-------------------------
class QueueWorker(Service, Tickable):
    def process(self):
        item = self.queue.peek()
        if item is None:
            return False
        if not item.ready():
            return False
        try:
            delivered = self.transport.deliver(item)
        except TemporaryDeliveryError as exc:
            item.attempts += 1
            item.last_error = type(exc).__name__
            item.next_retry = self.retry_policy.next_retry(item.attempts)
            self.queue.update(item)
            self.queue.nack(item)
            raise
        except PermanentDeliveryError:
            self.queue.ack(item)
            raise
        if delivered:
            self.queue.ack(item)
        else:
            self.queue.nack(item)
        return delivered
Il runtime chiama tick() circa ogni secondo. SQLiteQueueBackend.peek() scorre gli item in ordine di rowid e restituisce il primo item ready(), quindi non è stato riscontrato head-of-line blocking dovuto a un item con next_retry futuro.

6.3 RetryPolicy e diagnosi
--------------------------
class RetryPolicy:
    def __init__(self, base_delay=60, multiplier=2, max_delay=86400):
        ...

    def next_retry(self, attempts):
        delay = self.base_delay * (self.multiplier ** max(0, attempts - 1))
        delay = min(delay, self.max_delay)
        return datetime.now(UTC) + timedelta(seconds=delay)
Il backoff di default cresce 1m, 2m, 4m, 8m, 16m, 32m, 64m, 128m, 256m, 512m (8h32), 1024m (17h04) e poi resta limitato a 24h. La causa più plausibile del comportamento percepito come 'blocco' era quindi il normale exponential backoff diventato molto lungo dopo ripetuti TemporaryDeliveryError.
La rete non mostrava un'attesa infinita evidente: OnionTransport/Socks5Connection/TextConnection usavano timeout socket di circa 30 secondi. Inoltre TorStatus.ready non indica che uno specifico remote .onion sia raggiungibile.

6.4 Decisioni escluse
---------------------
- NON ridurre semplicemente max_delay: un backoff lungo resta utile quando un onion è realmente offline.
- NON risvegliare automaticamente tutta la queue quando TorStatus passa a ready: sarebbe un segnale locale troppo debole e potrebbe produrre retry storm.
- NON fare delivery diretto dal pulsante GUI: il tentativo deve passare dal QueueWorker normale.

7. SOLUZIONE IMPLEMENTATA: RETRY PENDING
==============================================================================

7.1 Contratto funzionale
------------------------
- Agisce soltanto sugli item sospesi, cioè con next_retry non None.
- Imposta next_retry = None, rendendo l'item immediatamente eleggibile al prossimo tick.
- Preserva attempts.
- Preserva last_error.
- Restituisce il numero di item risvegliati.
- Non effettua direttamente alcuna consegna.
La scelta di NON azzerare attempts è intenzionale: in caso contrario ripetuti click manuali potrebbero aggirare di fatto la logica di backoff.

7.2 Modifiche queue/backend
---------------------------

garlicsmtp/queue/sqlite.py
Aggiunto SQLiteQueueBackend.retry_pending(): sotto lock legge gli item, deserializza quelli con next_retry valorizzato, azzera soltanto next_retry, persiste il payload aggiornato, esegue commit e restituisce il conteggio.

garlicsmtp/queue/memory.py
Aggiunto MemoryQueueBackend.retry_pending() con la stessa semantica, iterando sulla deque in memoria.

garlicsmtp/queue/backend.py
Formalizzato retry_pending() come metodo astratto del contratto QueueBackend.

garlicsmtp/queue/manager.py
Aggiunto QueueManager.retry_pending(), delegato al backend corrente.

7.3 Modifiche application
-------------------------

garlicsmtp/application/controller.py
def retry_pending(
    self,
) -> int:
    return self.context.queue.retry_pending()
ApplicationController è il confine applicativo che raggiunge context.queue. La GUI non chiama direttamente QueueManager.

garlicsmtp/application/view_model.py
def retry_pending(
    self,
) -> int:
    return self.controller.retry_pending()
ApplicationViewModel delega al controller e restituisce il numero di item risvegliati. Non forza _status: il normale refresh resta responsabile dell'aggiornamento dello stato visualizzato.

7.4 Modifiche GUI
-----------------

garlicsmtp/gui/tk_mail_metrics_section.py
- Aggiunto ttk.Button con testo 'Retry pending'.
- Il pulsante è posizionato sotto le quattro metriche della MailMetricsSection.
- L'handler _retry_pending() chiama self.view_model.retry_pending().
- Nessun popup, refresh forzato o log aggiuntivo è stato introdotto senza test/requisito.
Percorso finale:
GUI Button.invoke()
    -> MailMetricsSection._retry_pending()
    -> ApplicationViewModel.retry_pending()
    -> ApplicationController.retry_pending()
    -> QueueManager.retry_pending()
    -> MemoryQueueBackend / SQLiteQueueBackend
    -> next QueueWorker tick
    -> normale delivery path

==============================================================================
- QueueWorker: se transport.deliver(item) restituisse False invece di sollevare TemporaryDeliveryError, il codice osservato esegue nack senza incrementare attempts/next_retry. È solo un'osservazione: non modificarlo senza evidenza riproducibile che sia coinvolto in un bug.
- Concorrenza GUI/runtime: SQLite retry_pending usa lock; Memory backend non ha lock aggiuntivi. Non introdurre sincronizzazione preventiva senza failure/test che la richieda.
- TorStatus.ready non è remote-onion reachability. Evitare automatismi basati solo sul passaggio a ready.
- Retry pending è un override manuale dell'attesa, non un nuovo algoritmo di retry e non una conferma di consegna.
- Non riaprire attachment, refresh Sent o core delivery senza un nuovo caso concreto.
