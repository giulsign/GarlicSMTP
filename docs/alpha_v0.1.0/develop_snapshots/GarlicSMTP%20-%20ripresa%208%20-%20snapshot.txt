4. REQUISITI DI SICUREZZA CONFERMATI
======================================================================

4.1 Recupero password - Recovery key offline generata con casualità
crittografica, mostrata esattamente una volta, con conferma esplicita
del salvataggio. - Mai conservare la recovery key in chiaro. - Account
developer già esistente: attivazione recovery dopo login valido, senza
reset account o Onion. - Recupero password con recovery key anche senza
vecchia password: impostare nuova password, invalidare la recovery key
precedente e generarne una nuova. - Conservare messaggi, allegati,
identità di firma/cifratura e identità Onion. - Recovery key non deve
diventare un metodo di login ordinario. - Rotazione della recovery key
anche dopo login valido, per sostituire una chiave smarrita. - Stesse
garanzie di sicurezza in developer e distribuzione; nessuna scorciatoia.

4.2 Gerarchia chiavi - DEK (Data Encryption Key) indipendente da
password e recovery key. - KEK derivata dalla password e KEK derivata
dalla recovery key proteggono la medesima DEK. - Reset password non
ricifra necessariamente tutti i messaggi: deve consentire il recupero
della stessa DEK. - Non usare hash di verifica password come se fosse
direttamente la chiave persistente. - Evitare di salvare DEK o recovery
key in chiaro. - Aggiornamenti delle protezioni della DEK atomici o
recuperabili dopo crash.

4.3 Cifratura a riposo - Proteggere mailboxes.db, sent.db, queue.db,
contenuti, metadati, allegati, eventuali WAL/SHM/journal/temp e backup
pertinenti. - Una copia del solo database non deve rivelare i
contenuti. - La sola cifratura della colonna payload NON soddisfa la
protezione integrale richiesta. - Nessun file temporaneo in chiaro non
controllato. - Le esportazioni esplicite di allegati in chiaro sono una
distinta operazione utente e vanno trattate come tali. - Validazione E2E
reale: ricezione -> chiusura GUI -> copia e verifica del database ->
riavvio -> recupero tramite chiave offline senza vecchia password ->
lettura dello stesso messaggio, con identità invariate. - Non simulare
con mock la cifratura nel test di accettazione.

5. RISULTATI DELLE ISPEZIONI NELLA PRESENTE CHAT
======================================================================

5.1 ApplicationBuilder e percorsi File:
garlicsmtp/application/builder.py - Costruisce MessageStore con
SQLiteMessageStoreBackend(paths.mailbox_database) e
AttachmentStore(paths.attachments_dir). - Costruisce QueueManager con
SQLiteQueueBackend(paths.queue_database). - Costruisce
FileEncryptionKeyStore(root_dir/‘encryption_keys.json’). - Costruisce
SigningIdentity(root_dir/‘signing.key’) e
EncryptionIdentity(root_dir/‘encryption.key’). - Il builder non riceve
attualmente una password per sbloccare gli archivi. File:
garlicsmtp/configuration/paths.py - DB ricevuti: data/mailboxes.db. - DB
inviati: data/sent.db. - DB coda: state/queue.db. File:
garlicsmtp/gui/application.py - Costruisce separatamente il MessageStore
dei messaggi inviati con
SQLiteMessageStoreBackend(context.paths.sent_mailbox_database) e
AttachmentStore. Altri accessi diretti a SQLiteMessageStoreBackend
identificati in: - garlicsmtp/cli/mailbox.py -
garlicsmtp/core/engine/bootstrap.py - garlicsmtp/gui/application.py -
garlicsmtp/application/builder.py Rischio: una modifica limitata al
builder non coprirebbe tutti i percorsi di apertura.

5.2 FileEncryptionKeyStore File:
garlicsmtp/security/encryption_key_store.py - MemoryEncryptionKeyStore e
FileEncryptionKeyStore conservano mappature hostname -> chiave pubblica
del corrispondente. - Persistenza JSON con chiavi pubbliche codificate
Base64. - Rifiuta la sostituzione silenziosa di una chiave pubblica
diversa per lo stesso hostname. - Salvataggio atomico via file
temporaneo, fsync e os.replace, permessi 0600; rifiuto di symlink. - NON
è il deposito della DEK e NON è un sistema di cifratura a riposo.

5.3 Database messaggi File: garlicsmtp/storage/sqlite/backend.py -
SQLiteMessageStoreBackend apre con sqlite3.connect(path,
check_same_thread=False), senza chiave di cifratura. - Schema messages:
id, mailbox, uid, payload TEXT NOT NULL, internal_date, flags,
verification_status, created. - Tabelle aggiuntive mailboxes,
mailbox_subscriptions e storage_metadata. - Migrazioni dello schema e
molte operazioni SQL dirette. - Attualmente non è dimostrata cifratura
integrale; i dati SQLite sono gestiti dal driver standard.

5.4 Coda File: garlicsmtp/queue/sqlite.py (letto integralmente) -
SQLiteQueueBackend apre con sqlite3.connect(self.path,
check_same_thread=False). - Tabella queue_items(id TEXT PRIMARY KEY,
payload TEXT NOT NULL). - enqueue/update/retry_pending serializzano
QueueSerializer.to_json(item) nel campo payload. - peek/retry_pending
deserializzano con QueueSerializer.from_json(). - ack cancella, close
chiude la connessione. - Nessuna chiave di cifratura all’apertura del
database.

5.5 Allegati File: garlicsmtp/storage/attachment_store.py (letto
integralmente) - save scrive content_path.write_bytes(content) in file
UUID.bin. - Scrive metadata_path.write_text(json.dumps({‘filename’,
‘declared_mime’})) in UUID.json. - list_for_message rilegge JSON e
bytes. - materialize_for_message crea file con il nome originale in una
directory di destinazione; verifica nomi non sicuri e duplicati. -
Contenuti e metadati attualmente scritti senza cifratura a riposo. - I
nomi delle directory sono derivati dal message_id, validato contro path
traversal. - Necessaria progettazione per cifratura autenticata,
migrazione e trattamento dell’esportazione in chiaro.

5.6 Dipendenze - requirements.txt e pyproject.toml dichiarano
cryptography>=46,<47. - SQLCipher/pysqlcipher non compare nei file
controllati con rg. - Non è stata verificata la
disponibilità/installabilità o compatibilità SQLCipher sulla VM Ubuntu
24.04. - La libreria cryptography da sola non rende cifrato un file
SQLite.

5.7 Cifratura E2EE attuale File: garlicsmtp/security/encryptor.py (letto
integralmente) - MessageEncryptor genera chiave X25519 effimera, scambia
segreto con chiave pubblica destinatario. - HKDF SHA-256, length=32,
salt=None, info=b’GarlicSMTP E2EE v1’. - Cifra JSON di headers e body
con ChaCha20Poly1305, nonce os.urandom(12). - AAD canonico JSON di
sender e recipients, per autenticarne il valore e l’ordine. - Messaggio
risultante contiene header X-GarlicSMTP-Encryption e corpo ciphertext
Base64. File: garlicsmtp/security/decryptor.py (letto integralmente) -
Controlla presenza, campi, versione, algoritmo, lunghezze chiavi e
nonce. - Ricostruisce segreto X25519 e chiave HKDF, decifra con AAD
envelope. - Verifica struttura JSON del payload decifrato. - Nessuna
necessità dimostrata di modificare E2EE per implementare at-rest.

5.8 PasswordHasher reale File:
garlicsmtp/security/auth/password_hasher.py (letto integralmente) -
Parametri Scrypt riportati in 3.1. - Serializza hash come campi separati
da ‘$’ con algoritmo, parametri, salt e hash Base64. - Verifica mediante
Scrypt e compare_digest; restituisce False per alcuni input non
validi. - Non produce né conserva una DEK.

7. CONCLUSIONI TECNICHE E DECISIONI ANCORA APERTE
======================================================================

CONCLUSIONI SUPPORTATE: - E2EE e cifratura a riposo sono problemi
separati. - Non riutilizzare chiavi private X25519, chiavi di sessione
E2EE o HKDF_INFO E2EE per at-rest. - ChaCha20Poly1305 e HKDF sono
primitive già usate e disponibili tramite cryptography. - Una DEK
indipendente dalla password è necessaria per recuperare gli archivi dopo
reset password. - I tre DB SQLite e gli allegati hanno attualmente vie
di persistenza non cifrate integralmente. - La cifratura per-record del
solo payload non coprirebbe struttura e metadati del database. - La
gestione di accessi diretti ai DB da GUI, CLI e bootstrap è un confine
progettuale fondamentale. - Il recupero deve preservare identità e dati,
non soltanto consentire nuovo login.

PROPOSTE, NON APPROVATE COME IMPLEMENTAZIONE: - Valutare SQLCipher come
candidato alla cifratura integrale di tutti i DB SQLite. - Usare
cifratura autenticata per allegati e metadati, con separazione
crittografica dei contesti. - Un possibile modulo separato
garlicsmtp/security/at_rest_cipher.py con test
tests/test_at_rest_cipher.py. - Primo gruppo di verifiche primitive:
round-trip, chiave errata, ciphertext manomesso, nonce fresco; test
successivi di persistenza e recovery. - NON partire con un RED
dipendente da SQLCipher prima di validare disponibilità e packaging
Ubuntu 24.04.

DECISIONI ANCORA DA PRENDERE: - Motore cifratura DB e dipendenze
installabili/distribuibili. - Formato versionato della DEK avvolta da
KEK password/recovery, KDF e gestione AAD. - Protezione di chiavi
private e identità Onion senza alterare la loro continuità. - Migrazione
atomica/crash-safe dei dati developer in chiaro verso archivi cifrati. -
Politica di file temporanei, journal, WAL, backup, esportazioni e
residui di plaintext. - Sblocco solo dopo login, gestione ciclo di vita
chiavi e accesso CLI/bootstrap. - Gestione credenziali e recovery UI
(mostra una volta, conferma salvataggio, reset, rotazione). - Strategia
per impedire lettura di dati preesistenti in chiaro dopo migrazione. -
Test E2E realistici su developer e Ubuntu 24.04.

8. PUNTO ESATTO DI ARRESTO
======================================================================

L’utente ha richiesto espressamente di analizzare encryptor.py,
decryptor.py, test_message_encryptor.py (prime 240 righe) e
password_hasher.py, fermandosi prima di generare codice o test. La
richiesta è stata rispettata.

L’ultimo giudizio tecnico è: - Non riscrivere MessageEncryptor o
MessageDecryptor. - Creare in futuro un dominio crittografico separato
per i dati a riposo. - Non confondere PasswordHasher con una chiave per
decifrare i dati. - Valutare cifratura integrale SQLite, senza scegliere
prematuramente SQLCipher. - Prima di qualunque codice/test, leggere
sorgenti e test reali specifici dell’intervento. - Nessun nuovo
RED/GREEN è stato scritto o eseguito in questa chat.
