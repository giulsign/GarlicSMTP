Priorità alta
1. Consolidare SELECT / EXAMINE

È esattamente il prossimo step che abbiamo deciso.

Adesso i due metodi duplicano:

autenticazione;
mailbox lookup;
FLAGS;
PERMANENTFLAGS;
EXISTS;
RECENT;
UIDVALIDITY;
UIDNEXT;
UNSEEN.

La differenza reale è quasi soltanto:

SELECT  → read_only=False → [READ-WRITE]
EXAMINE → read_only=True  → [READ-ONLY]

Quindi estrarre un helper ora è refactoring giustificato, non sovraengineering.

2. UIDVALIDITY reale

Oggi:

uid_validity() -> 1

è sostanzialmente una costante.

Per un server realmente persistente dovrebbe esserci una UIDVALIDITY per mailbox, persistita e aggiornata correttamente quando la mailbox viene ricreata.

Questo è un gap importante.

3. MODSEQ reale

Analogamente:

highest_modseq() -> 1

è ancora sostanzialmente placeholder.

Se vogliamo mantenere/esporre davvero HIGHESTMODSEQ, bisogna introdurre una sequenza di modifica persistente.

In alternativa possiamo non pretendere supporto avanzato CONDSTORE/QRESYNC.

4. AUTHENTICATE / TLS

Mancano ancora:

AUTHENTICATE
STARTTLS

Questo va affrontato come fase architetturale separata, perché STARTTLS riguarda socket/connection handler, non semplicemente IMAPProtocol.

Non conviene inserirlo come un altro metodo di 30 righe.

5. Capability audit finale

Dobbiamo far sì che CAPABILITY dichiari esattamente ciò che il server offre.

Un caso da verificare è IDLE: il comando esiste, ma va controllato che venga anche pubblicizzato nella capability finale.

La sequenza che vedo più efficiente è:

2. audit CAPABILITY / IDLE
3. UIDVALIDITY persistente

7. TLS + authentication architecture
8. hardening end-to-end
9. packaging/documentazione

E terrei fuori dalla critical path:

BODYSTRUCTURE multipart completo

Quindi siamo in un punto buono: la fase “aggiungiamo continuamente comandi IMAP” può praticamente considerarsi conclusa. Ora conviene consolidare ciò che esiste e chiudere i pochi gap strutturali rimasti.

Il prossimo passo può essere esattamente quello concordato: estrarre un helper che costruisce le risposte comuni di SELECT e EXAMINE, senza modificare il comportamento osservabile e mantenendo la suite verde.

terminata questa aprte possiamo considerare concluso il lavoro di sviluppo del sistema e passare alla creazione di una gui per invio, ricezione, lettura e ricerca delle mail?

Sì, quasi. Terminato il consolidamento IMAP che stiamo facendo, io considererei conclusa la fase di sviluppo del motore mail/backend e passerei alla GUI, ma con una distinzione importante: prima della GUI chiuderei ancora pochi punti strutturali, non nuove feature.

In pratica, eviterei di continuare ad aggiungere comandi IMAP o funzionalità MIME. Il backend ha già abbastanza superficie per supportare una GUI reale: invio SMTP, ricezione/store, mailbox, flag, lettura, ricerca, copy/move/delete, persistenza SQLite e trasporto Onion.

Prima di dichiarare definitivamente “backend completo”, chiuderei questa breve checklist:

estrazione helper comune SELECT / EXAMINE;
audit finale CAPABILITY (in particolare verificare IDLE e non dichiarare capacità non realmente supportate);
rendere UIDVALIDITY persistente per mailbox, invece della costante 1;
decidere cosa fare di HIGHESTMODSEQ: implementarlo realmente oppure non presentarlo come funzionalità avanzata;
una suite end-to-end finale che copra almeno SMTP → Store → IMAP;
stabilizzare l’interfaccia che userà la GUI, evitando che la GUI parli direttamente con dettagli interni dello storage.

STARTTLS / AUTHENTICATE meritano una considerazione separata. Se GarlicSMTP deve essere usato solo localmente sul computer dell’utente e l’esposizione di rete è controllata, possono anche essere affrontati dopo la prima GUI. Se invece il server IMAP/SMTP deve essere esposto su rete normale, li considererei prerequisiti di sicurezza prima di chiamare il sistema “finito”.

Per Linux punterei a un risultato del tipo:

./install.sh

oppure, meglio ancora in una fase più matura:

sudo apt install garlicsmtp

con installazione automatica di dipendenze, directory dati/config/log, database iniziale, configurazione Tor/SOCKS se prevista, servizi di sistema, launcher GUI e procedura di primo avvio.

L'obiettivo finale dovrebbe essere che l'utente non debba conoscere Python, virtualenv, SQLite, SMTP, IMAP o Tor per utilizzare GarlicSMTP.

Quindi aggiornerei mentalmente la roadmap così:

1. consolidamento backend
2. backend freeze
3. application/service layer
4. GUI
5. integrazione GUI/backend
6. configurazione first-run
7. packaging Linux
8. installer/autoconfigurazione
9. test su Linux pulito
10. release ready-to-use

E terrei Windows fuori dalla critical path della v1: possiamo progettare fin da subito percorsi/configurazione in modo portabile, ma packaging Windows, servizi e installer li affrontiamo nella versione successiva.

Una cosa importante: quando inizieremo la GUI, conviene già evitare scelte che rendano difficile il packaging. Ad esempio niente path assoluti, niente dipendenze implicite dalla .venv, configurazione centralizzata e un unico entry point applicativo.

Quindi sì: “autoinstallante, autoconfigurante e ready-to-use su Linux” entra da ora tra i criteri di completamento del progetto, insieme alla GUI.
